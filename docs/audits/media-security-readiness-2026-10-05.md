# Medical Upload And Media Security Readiness

Reviewed October 5, 2026 (Asia/Tehran), following the user's explicit concern about media handling and security breaches. This is a bounded security review before medical UI delivery. No actual compromise has been established; the findings below distinguish reproduced behavior, missing integrations and conditional exposure.

## Decision

**Follow-up status:** the [first hardening slice](../deployment/demo-media-hardening-2026-10-05.md) now closes the reproduced generic signed-route access, stale-byte/missing-blob clean acceptance and download privacy-header gaps. Focused coverage passes 37 tests/259 assertions; runtime confirms alternate routes are absent. The findings below preserve the pre-fix review evidence. Actual antivirus, content/capacity controls, self-hosted S3 deployment and operational/HIPAA readiness remain open.

Medical upload/scan/review delivery remains gated on media security. Existing role/booking/payment acceptance is unchanged. A database `clean` flag and the existing passing medical tests do not establish that a real scanner approved the exact bytes delivered to a doctor or patient. Do not demonstrate a manual clean-state shortcut or submit real patient documents during development verification.

## Existing Safeguards

- Medical uploads use the private disk outside the public document root; its dedicated configuration has serving disabled. The deployed `public/storage` link points to `storage/app/public`, not private storage.
- Authenticated active-account API routes and controller/service ownership checks reject other patients, other doctors and generic admins. Cross-reservation/request/file checks are explicit. Scoped medical resources omit paths, disk, original filename, checksums, scanner internals and owner IDs.
- Medical uploads start quarantined with a generated filename, detected PDF/JPEG/PNG MIME, a 10 MiB application validation limit, checksum and server-controlled retention. Clients cannot submit scan state or storage/ownership facts.
- Dedicated medical downloads block quarantined/infected/failed, archived, expired, missing and non-private blobs. Patient outcome downloads also require publication. Upload/storage rollback compensation and access/transition auditing are present.
- Fresh isolated baseline: 21 existing medical/file/public-media tests pass with 181 assertions. This verifies their current contracts, including ownership and quarantine denials; it does not close the new gaps below.

## Findings And Exact Scope

| Release blocker | No real scanner is integrated | `ReservationFileService::recordScan` accepts a result enum directly, checks the row's quarantined state and records it. No application scanner adapter/job or production call site was found. Existing tests/factories simulate clean results. This is a missing integration rather than an exposed public scan callback. |

| High, conditional | A second filesystem alias bypasses medical controls | Both `local` and `private` root at `storage/app/private`, but `local` has `serve=true`. Isolated guest GET with a valid server-generated signature reads a quarantined fixture; valid signed PUT overwrites a clean fixture without re-quarantine, checksum update or medical audit. Unsigned GET is denied. No current application endpoint issuing these URLs was found. Possession of a legitimate signed URL or signing capability is a prerequisite; there is no demonstrated unsigned internet bypass. Production Nginx's public-storage alias may change reachability; no production exploit is claimed. |
| Medium | Dedicated download responses lack explicit medical privacy headers | Isolated service response has attachment disposition, but no explicit `no-store` or `X-Content-Type-Options: nosniff`. Active development backend Nginx does not add nosniff; the static admin's header does not protect backend file responses. Production Nginx defines nosniff, but dedicated no-store behavior still needs explicit verification. |
| Medium | Resource limits and content treatment are incomplete | The upload route has no explicit media throttle or per-request/account bytes/file-count quota. MIME/size validation is present; structural validity, decoded image dimensions, PDF active content, encryption/password handling, metadata/EXIF policy and scanner CPU/time/memory limits are not implemented here. | Operational | Runtime upload limits disagree with application validation | Active PHP CLI reports upload_max_filesize 2M and post_max_size 8M; application allows 10 MiB and Nginx accepts 50M. Related public media is a separate privacy boundary: `PublicMediaService` preserves uploaded image bytes and archives only database metadata; original public URLs/bytes are not revoked by that archive operation. It has no service-level authorization and no current application controller caller was found. Treat these as integration requirements before exposing public upload endpoints, not a demonstrated current patient upload exploit. Medical originals must never be routed through that public service.

## Remediation Order

1. **Close alternate access and establish byte integrity.** Disable generic signed serving/upload for the private-root alias after checking current callers; preserve public assets. Require a canonical private path and immutable blob identity. Scan the stored bytes, associate verdict with that digest/version, and stream the same verified immutable bytes at download. A check followed by reopening a mutable path is still a race. Add explicit no-store, attachment, nosniff and suitable restrictive content policy; retain audited, owner-scoped endpoints.
2. **Implement actual internal scanning with failure behavior.** Choose the scanner and isolation arrangement explicitly before adding dependencies or Docker services. Medical documents must stay local to the approved processing environment; do not send them to an external malware-analysis service without explicit approval. Record engine/signature version, content digest and result. Timeout, unavailable engine, unreadable/changed blob, unsupported or uninspectable content must remain unavailable; no clean fallback. Authenticate any asynchronous result authority and bind it to the exact pending file/version. Test stale/duplicate/mismatched verdicts and replacement/archive races.
3. **Set the narrow content and capacity contract.** Confirm required formats and maximum bytes/files, whether encrypted PDFs are rejected, and preview/metadata treatment. Add bounded request/account quotas and rate limits, align proxy/PHP/application limits, and test malformed/mislabeled/oversized input without flooding live services. Image validation must bound decoded dimensions; PDF processing must restrict active content and external fetches. Preserve medical originals and provenance; any sanitized preview must be a separate private derivative linked to its original.
4. **Verify storage/privacy operations and the UI.** Inspect permissions, logging, backup access, encryption/key ownership and retention behavior with concrete deployment evidence. Expired retention currently prevents access; it is not proof of physical purge from disks/backups. Do not delete historical records or introduce purge jobs implicitly. Only then connect the existing Velzon upload/review/outcome presentation and accept the real workflow.

The approach follows [OWASP's File Upload guidance](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html): layered validation, controlled storage/access, size limits and malware/content checks. Scanner approval cannot establish confidentiality, authorization or medical correctness by itself.

## Verification And Reproduction

- Existing focused suite: **21 tests / 181 assertions**, 15.56 seconds, as www-data with APP_ENV=testing, SQLite `:memory:`, array session/cache and PHPUnit result cache disabled.
- Temporary security characterization: **4 reproductions / 16 assertions**, 11.55 seconds, same isolation. They confirm current unsafe/conditional behaviors; they are not passing security release gates. Harmless synthetic fixtures only; no malware, real medical content, live uploads or live database mutations.
- Signed URL probes use application-generated signatures in the isolated test process and fake disks. They do not discover or leak application keys or issue live URLs. Unsigned retrieval is denied. Signed upload demonstrates an overwrite capability only when a valid upload URL is supplied.
- Source was unchanged. The temporary test was removed after review. Test-only storage was placed under `/tmp/checkupino-media-audit-20261005` to avoid the existing root-owned fake-disk tree; it is not a runtime storage setting.
- Read-only runtime route/configuration inspection confirms the two generic storage routes, medical route middleware, public symlink target and CLI limits. No scanner dependency installation, Docker build/Compose action, live scan result, cache reset, migration/reseed or permission change was performed.
- Record: [review evidence](../deployment/evidence/media-security-review-2026-10-05.json). Historical Phase 1 medical acceptance remains valid for its original contracts; the findings identify the required integration/security gate before medical demo delivery.
