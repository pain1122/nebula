## M00-M02 - Identity, Framework Operations, And Authorization

### Before

- The initial Laravel user migration created only name/email/password, reset tokens, and sessions.
- A later migration added required patient-style profile columns, the obsolete `users.role`, and an inert mass-assignable `users.tenant_id`.
- Two later migrations added `patient_status` and then removed `users.role` again.
- Sanctum tokens lived in another later migration.
- The user table had no stable public identifier and no authentication-level account state.
- The user migration dropped `users` before session/reset tables during rollback.
- Staff identities had to provide patient-oriented birth/NID/contact fields at the database layer.

### After

- `0001_01_01_000000_create_users_table.php` is the complete marketplace M00 baseline for users, password reset tokens, sessions, and Sanctum personal access tokens.
- `users.public_id` is a unique ULID generated by `User` while the internal bigint ID remains available for local foreign keys.
- `account_state` is separate from nullable patient lifecycle state and uses `active`, `suspended`, or `closed` through `AccountState`.
- Account-state change time, actor, reason, and closure time have dedicated columns that are not broadly mass assignable.
- Patient/profile columns are nullable at schema level. Patient request paths may still require them; staff rows no longer need fake patient data.
- `users.role` and `users.tenant_id` are absent. Spatie remains the only role authority and isolated tenant databases own their own identities.
- Personal access tokens are created and dropped with M00; rollback drops dependent auth tables before users.
- Stock Laravel cache/job tables remain the M01 group and the package-compatible Spatie tables remain M02 with teams disabled.

### Removed Superseded Migrations

- `2025_11_16_111142_create_personal_access_tokens_table.php`
- `2025_11_30_083045_add_profile_fields_to_users_table.php`
- `2026_06_03_102531_add_patient_status_to_users_table.php`
- `2026_06_03_114235_drop_role_from_users_table.php`

### Why

- A fresh database should reach the final identity shape directly instead of adding and removing authority/ownership columns historically.
- Marketplace `tenant_id` would recreate the cross-database ownership ambiguity explicitly rejected by the product contract.
- Patient commercial/lifecycle state must not accidentally control authentication; the new account state has one security meaning.
- Public IDs prevent future APIs from exposing sequential database keys.
- Nullable patient fields correctly model root-admin, admin, and doctor identities without weakening patient endpoint validation.

### Compatibility And Follow-Up

- Existing auth, registration, token, root-admin, step-up, and audit behavior remains compatible.
- `patient_status` remains temporarily available for current patient/admin APIs but is not an authentication state.
- Runtime transition/revocation enforcement for `suspended` and `closed` accounts will be added and verified before the Phase 1 gate.
- Account-state transition/revocation enforcement is deliberately not claimed by this schema group; it remains required before the Phase 1 gate.

### Verification

- `FoundationIdentitySchemaTest`: schema shape, public ULID/default account state, nullable non-patient identity fields, and M00-M02 tables.
- `FoundationIdentityMigrationLifecycleTest`: focused M00-M02 apply/rollback/reapply.
- Existing authentication, registration, bearer-token, admin-user audit, and admin-user step-up regression suites.
- Disposable MySQL M00-M02 `migrate:fresh`, rollback, and reapply passed through an internal-network verification container, avoiding the Windows host-port conflict on `3307` without changing project configuration.

## M10, M20a, And M30 - Marketplace Directory, Doctor Ownership, And Catalog

### Before

- There was no hospital directory or doctor-to-hospital workplace model.
- A doctor had one `specialty_id`, a JSON `availability` field, and no unique constraint on `user_id`.
- Doctor deletion cascaded from user deletion, which could participate in historical reservation loss.
- Doctor/checkup eligibility was global through `checkup_doctor`; it could not vary by hospital.
- The specialty rollback altered columns but never dropped the table.
- Category/checkup archive and nullable-category rules were spread across three late alteration migrations.
- Checkup price was a 32-bit integer with no currency or default duration.

### After

- New marketplace-only `marketplace_hospitals` and `hospital_listing_requests` tables model the curated directory and doctor requests without creating hospital-admin ownership.
- Hospital records include public ULIDs, timezone/location/filter fields, active/archive metadata, and no tenant database credentials or business data.
- Listing requests belong to marketplace users, use a typed pending/review lifecycle, and may point to the resulting directory hospital after review.
- Doctor profiles have public ULIDs, unique/restrictive user ownership, verification metadata, and soft archive.
- `doctor_specialty` adds multi-skill filtering while `doctor_profiles.specialty_id` remains the single display/primary specialty used by current APIs.
- `doctor_workplaces` is the unique doctor/hospital parent for future services, schedules, and reservations.
- Specialties now have public IDs, active/archive state, and a real table-dropping rollback. Name and slug remain globally unique for the current non-localized taxonomy; future translations should use a separate localization structure.
- Category/checkup creation migrations now directly contain public IDs, archive fields, soft deletes, nullable category with `SET NULL`, bigint minor-unit price, currency, and default duration.
- The three superseded catalog alteration migrations were removed.

### Why

- Marketplace hospitals are filter/directory records, not tenants and not authorization owners.
- A workplace gives the same doctor independent per-hospital service and schedule parents without any tenant query.
- Multiple specialties enable clean doctor filtering while retaining an explicit primary display specialty for the current simple UI.
- Restrictive doctor ownership and nullable category links preserve historical records.
- Folding final catalog behavior into initial table creation removes driver-specific alter SQL and guarded rollback traps from an empty-database baseline.

### Compatibility And Follow-Up

- Existing catalog archive/detach/reassign behavior and current booking tests still pass.
- Legacy JSON `doctor_profiles.availability` and global `checkup_doctor` were removed by M20b. The unchanged Blade JSON input is now a backend compatibility adapter that reads/writes normalized working-window rows.
- No hospital directory/admin UI was added; Phase 1 remains backend-only.

### Verification

- New directory/catalog schema and lifecycle tests pass on SQLite.
- Existing catalog destructive-data, booking-risk, and listing/filter tests pass: 26 tests, 198 assertions in the combined focused run.
- Disposable MySQL apply/rollback/reapply passes for M00 + M10 + M20a + M30.
- MySQL initially rejected Laravel's generated doctor-workplace unique-index name for exceeding 64 characters. The migration now uses the explicit portable name `doctor_workplace_hospital_unique`.

## M20b, M40, And M50 - Workplace Scheduling, Reservations, And Payments

### Before

- Doctor/checkup eligibility was global and schedules were stored as unqueryable JSON on the doctor profile.
- Reservations referenced patient, doctor, and checkup with cascading deletes and no workplace, hold expiry, duration/timezone, immutable snapshots, or reschedule history.
- Reservation vocabulary mixed `paid`/`done` with payment state and the `canceled`/`cancelled` spelling drift.
- Every reservation had one loose `payments` row; provider retries, callback receipts, canonical success, idempotency, and adjustments had no schema.
- Every reservation, including cancelled/old pending rows, participated in the generic doctor overlap query.

### After

- `doctor_workplace_checkup` scopes service eligibility, optional price/currency/duration overrides, and active state to one doctor workplace.
- `doctor_working_windows` stores indexed weekday/time/effective-range rows. Existing Blade schedule JSON is translated by `DoctorScheduleService`; it is no longer persisted on doctor profiles.
- Reservations require a workplace and preserve hospital/doctor/checkup/category/price/currency snapshots, duration, timezone, and a one-hour `hold_expires_at`.
- Reservation statuses are `pending`, `confirmed`, `completed`, `cancelled`, and `expired`. Payment state remains separate.
- Conflict queries block `confirmed` reservations and only unexpired `pending` holds. Cancelled, completed, expired, and stale pending rows release availability.
- Restrictive patient/doctor/workplace/checkup foreign keys retain history; schedule changes have an append-oriented actor/reason/before/after table.
- Booking supports an optional idempotency key, locks service/catalog/doctor selection, requires an exact configured duration and generated workplace slot, and writes immutable snapshots with one payment summary transactionally.
- `reservation_payment_summaries` enforces one summary per reservation. `payment_attempts` supports repeated provider attempts with provider-scoped idempotency/reference uniqueness; provider events and adjustments have separate retained tables.
- The `Payment` class remains a compatibility class name but maps explicitly to `reservation_payment_summaries`; there is no legacy `payments` table.
- Rating options moved into the M40 creation group and gained public IDs.

### Why

- Workplace ownership is required for one doctor to offer different services, prices, and schedules at different marketplace hospitals.
- A one-hour pending hold prevents indefinite slot blocking while preserving a retry window for provider errors.
- Reservation and payment state must not encode each other; confirmation requires verified payment but is an appointment lifecycle state.
- Immutable snapshots keep history understandable after hospitals, doctors, categories, or prices change.
- Multiple attempts and append-only provider evidence are prerequisites for safe callbacks, reconciliation, refund, and audit flows.

### Compatibility And Follow-Up

- Existing Blade pages were not changed. Backend adapters resolve the single eligible workplace used by the current simple UI; APIs accept `doctor_workplace_id` and require it when more than one eligible workplace exists.
- The `Payment` compatibility class avoids rewriting every current response at once; explicit API Resources remain a later foundation requirement.
- Payment provider callbacks and status-transition services are not claimed by this schema group.
- Factories/seeders still need item 7 rebuilding for deterministic hospitals/workplaces/windows/payment attempts.

### Verification

- New tests prove legacy tables are absent, workplace/service/window tables exist, booking creates one-hour holds and immutable snapshots, expired pending holds release slots, and repeated attempts preserve one summary while duplicate provider idempotency fails.
- Focused lifecycle apply/rollback/reapply passes on SQLite and MySQL.
- SQLite rollback required column-based FK removal while MySQL required the explicit short constraint name; the payment migration handles both drivers.
- MySQL caught and fixed overlong generated schedule-history foreign-key names.
- Full backend suite passes after the rewrite: 80 tests, 414 assertions.

## M60 And M70 - Questionnaires, Leads, And Medical Retention

### Before

- Public questionnaire definitions returned every choice's internal score.
- Submission validation allowed missing questions and duplicate answers.
- Questionnaire definitions/submissions had no public IDs or version contract; physical questionnaire deletion cascaded into submission history.
- Guest tokens were stored in plaintext and appeared in raw model responses/search paths.
- Leads had no consent or retention metadata.
- User medical profiles and reservation notes/files cascaded from physical parent deletion.
- Reservation files stored only a public-looking path and label, with no private-storage, scan, checksum, uploader, classification, or retention contract.

### After

- Public definitions serialize choice ID/text/order only. Scores, recommendation thresholds, and conditions remain server-side.
- Submission requires exactly one valid choice for every questionnaire question. The completed response may return the approved total score and recommendation.
- Questionnaires, questions, choices, recommendations, submissions, leads, profiles, notes, and files have public ULIDs.
- Questionnaire version/publication metadata is snapshotted into submissions; submission foreign keys restrict physical questionnaire deletion.
- Guest-token material is stored only as a SHA-256 hash and hidden from model serialization.
- Leads include consent source/time/state and retention fields; the current public form still needs an explicit consent-product flow before that metadata can be claimed as granted.
- Medical profiles, notes, files, and submissions use restrictive retention-safe foreign keys.
- File metadata now reserves private disk/path, safe/original names, MIME/extension/size/checksum, uploader, classification, quarantine/scan state, and retention/archive fields. No upload workflow is claimed yet.

### Why

- Revealing per-answer scores lets users intentionally manipulate screening outcomes.
- Versioned snapshots and restrictive keys preserve what the user answered and saw even after questionnaire edits.
- Medical and questionnaire history must survive catalog/account archival and cannot depend on ordinary CRUD cascades.
- Private-file security needs schema support before upload/download UI is built.

### Verification

- Public resource tests prove scores/rules are absent while completed results remain available.
- Duplicate/missing-answer regression coverage is included.
- Schema tests prove retained questionnaire history and medical-profile account-deletion restrictions.
- SQLite focused lifecycle and full marketplace MySQL lifecycle pass.

## M80 And M90 - Platform Primitives And Monitoring

### Before

- Audit rows had no public ID, actor/subject public snapshots, reason/outcome, or correlation ID.
- Audit filtering removed only a few top-level secret keys; nested secrets, phone/NID, questionnaire answers, medical values, and file paths could survive.
- Settings, features, outbox, and tenant monitoring had no schema.
- `active`/`suspended`/`closed` existed only as an approved contract, not an authentication boundary.

### After

- Audit events include public IDs, actor/subject stable references, reason/outcome, and correlation IDs.
- Redaction recursively removes secrets/tokens/sessions, phone/NID/birth/address/profile data, medical answers/diagnoses, and storage paths while retaining allowlisted operational context.
- Typed setting definitions/values, a feature registry, and a reliable outbox baseline are available for future admin, mobile, content, commerce, and integration work.
- Marketplace `tenant_instances`, feature overrides, and health snapshots store only identity/subscription/version/health/sanitized aggregates. Their schema contains no patient/reservation/payment/questionnaire/medical foreign keys.
- Browser/API login rejects inactive users. Authenticated access applies `account.active`; suspended/closed users lose all Sanctum tokens and the current browser session when checked.

### Limits Kept Explicit

- No root-admin account-state mutation endpoint/UI was added in Task 6.
- Current middleware makes suspended/closed sessions unusable on their next request. A mutation-time Redis session index/purge service is still required before claiming proactive deletion of every remote browser-session key.
- Settings/feature/monitoring operational APIs and admin UI are later tasks.

## Separate Minimal Tenant Foundation

### Before

- `users.tenant_id` was an inert marketplace column and no tenant schema existed.

### After

- `config/database.php` defines an explicit tenant connection configured independently from marketplace storage.
- `database/migrations/tenant` contains six reversible groups: installation/singleton hospital profile, local auth/sessions/tokens, local Spatie-compatible roles, local framework tables, local settings/signed entitlement cache, and local audit/outbox.
- Tenant users are local and contain no marketplace user ID, `tenant_id`, or role column.
- The tenant path contains no marketplace hospital directory, doctor workplaces, reservations, payment tables, questionnaires, submissions, or medical files in Phase 1.
- Marketplace and tenant migration repositories execute against separate databases through `--database=tenant --path=database/migrations/tenant`.

### Why

- This preserves the strict hospital data boundary now without implementing tenant product workflows early.
- Local authority and entitlements prevent marketplace admins or client-selected tenant IDs from becoming tenant-data authorization shortcuts.
