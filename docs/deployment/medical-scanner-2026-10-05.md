## Design And Source Behavior

- Select ClamAV 1.5.4 for this evaluation. The official release fixes parser/security defects affecting earlier releases. The official Docker Hub tag API reports linux/amd64 manifest `sha256:7659dcb0db47941d3cf8336af84bbb63c7e70b76fc00601774358412b42ed186`; Compose pins that exact artifact. A Docker manifest request returned a country-restricted registry 403; host-side official tag metadata succeeded and the subsequent user-run image pull succeeded. [Release](https://github.com/Cisco-Talos/clamav/releases/tag/clamav-1.5.4), [official image metadata](https://hub.docker.com/v2/repositories/clamav/clamav/tags/1.5.4/).
- Send `INSTREAM` chunks through a Unix socket mounted only by the scanner/check/worker containers. ClamAV has no application mount, patient file paths, S3 credentials, backend network, TCP listener or published host port. Its separate network supports official definition updates. The socket has mode 0666 within that restricted shared volume, permitting the separately unprivileged PHP UID without modifying existing users/groups; worker/check mount it read-only. This is an evaluation boundary, not host-root isolation. [Protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html).
- `ClamdScanner` receives the already verified private-file snapshot, streams chunks no larger than 64 KiB and hashes exactly those bytes. It accepts only strict clean/infected responses; encrypted/scan-limit heuristic verdicts are failed/blocked. Malformed/error/truncated/appended responses are failures. Socket resources close on all paths and raw response/signature/socket details do not enter exceptions or audit.
- Loaded engine version must be exactly 1.5.4, definitions no older than 48 hours and no more than five minutes in the future. Version/database identity is checked before and after each scan; a reload between them rejects that attempt. Definition age is checked on every scan, including when the daemon stays up after an updater problem.
- Client execution has one monotonic deadline, default 45 seconds, configurable only within 1..45; connection establishment is at most two seconds. Worker job timeout is 120 seconds and queue retry visibility is 180 seconds. The daemon's MaxScanTime setting applies only to ZIP scans in this version: the client deadline does not prove that every daemon parser stops at that time. Daemon stall recovery and capacity measurements remain open. [Versioned configuration](https://raw.githubusercontent.com/Cisco-Talos/clamav/clamav-1.5.4/etc/clamd.conf.sample).
- Startup refreshes official definitions before starting clamd. FreshClam checks 12 times/day, with bounded connect/receive/retry settings. Concurrent database reload is disabled to reduce simultaneous engine memory use. The container exits if updater or scanner dies. A shared definitions volume and an initialization service operate only on newly created scan volumes. No existing volume is chowned or reset. [FreshClam settings](https://raw.githubusercontent.com/Cisco-Talos/clamav/clamav-1.5.4/etc/freshclam.conf.sample).
- `MEDICAL_SCAN_ENABLED` defaults false and the live .env is unchanged. Enabling it inserts an encrypted `ScanReservationFile` job containing only opaque file identity/digest. The dedicated `medical-scan` database connection uses the same database transaction as the file row, with after_commit=false; no separate scheduler or after-commit dispatch gap is introduced. Unsafe driver/queue/table/database/retry configuration is rejected. Dispatch failure rolls back file/audit/job rows and compensates the storage object.
- The worker command names only the medical-scan connection and queue. It cannot consume default/payment/notification jobs through this command. Three attempts use 15/60-second backoff; transient errors retain quarantine. Exhausted failure records Failed when possible; failed audit/database recording still leaves access blocked. Archived, expired, missing, changed-identity or already-terminal records are skipped. Duplicate deliveries do not produce duplicate clean transitions/audit.
- Successful verdicts go through existing locked `recordScan`, including a fresh verification for Clean. The audit records digest, engine version and database version/update time, alongside existing scoped lifecycle facts; no original filename/path/signature/content is recorded. Production scan callers now exist in source; no public scan callback or manual clean command was added.

No new PHP package or schema migration is required. The existing Velzon interface, app/nginx/DB/Redis/admin/media containers, live private driver and NebulaNV remain unchanged. Existing synthetic SQLite tests may create their own in-memory schema; no live migration is part of this work.
