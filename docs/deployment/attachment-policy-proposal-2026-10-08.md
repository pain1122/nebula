# Medical Attachment Policy Persistence Proposal

October 8, 2026, Asia/Tehran. Original source-only approval is followed by explicit approval to apply the exact live migration while retaining rollback compatibility. Both source and live schema are now verified; [acceptance, evidence and rollback](medical-attachment-policy-2026-10-08.md). No live backfill/reset/reseed/new UI/scanning activation. The proposal below records the original reviewed scope; its pending-approval wording is historical.

## Bounded Scope

Use the existing medical request as the authorized form record and its existing `file` upload field. Persist an immutable server-generated policy when the assigned doctor creates a request. A doctor can request narrower MIME/size constraints; the server resolves the medical section, owner and reservation and validates every constraint against current root/operator/scanner authority. Uploaders never select an arbitrary section or supply a policy snapshot. No generic form builder, questionnaire attachment extension, new panel route or public SEO page is included.

The first useful case is a PDF attachment limited to 1 MiB within today's 10 MiB medical section. Optional inputs on the existing doctor request-create API are:

```json
{
  "attachment_rules": {
    "allowed_mime_types": ["application/pdf"],
    "max_bytes": 1048576
  }
}
```

Omitting `attachment_rules` captures the current medical section as the request's default policy. Reject unknown fields, unsupported types, duplicate/empty type lists, noninteger/nonpositive sizes, and any increase beyond section/operator/scanner authority. Policy output is generated by the service, not mass-assigned from that input.

## Exact Schema Addition For Review

Add two nullable columns to `reservation_medical_requests` in a new additive migration; keep existing migrations intact:

```php
Schema::table('reservation_medical_requests', function (Blueprint $table): void {
    $table->json('attachment_policy')->nullable();
    $table->char('attachment_policy_revision', 64)->nullable();
});
```

Proposed stored snapshot:

```json
{
  "version": 1,
  "field": "file",
  "section": "medical",
  "section_revision": "<current server section revision>",
  "allowed_mime_types": ["application/pdf"],
  "max_bytes_by_mime": {"application/pdf": 1048576}
}
```

The revision is SHA-256 over a deterministic canonical serialization of this snapshot. Snapshot/revision are written together with request creation and its audit in the existing transaction. Block later snapshot/revision mutation through the model/service; changing attachment requirements creates a new authorized request and retains the old history. Audit only safe IDs, state and policy revision, with no patient/file content. No new columns on files, multipart sessions or reports in this slice.

Nullable columns avoid a migration-time backfill or rewriting old medical records. Legacy/missing snapshots are explicitly distinguishable; a request without a valid matching snapshot cannot claim field-policy acceptance. The intended new field-policy upload path fails closed for a missing/invalid/mismatched snapshot and requires an ordinarily issued request. Live currently has zero medical requests, so no conversion is required. Before activation, review source compatibility for any legacy medical API callers; never silently manufacture historical snapshots.

## Enforcement And Policy Changes

Resolve request and field from authorized server records. Preserve patient ownership, same-reservation binding, open-request state and assigned-doctor authority. Both API validation and upload service use the same resolver; direct service callers cannot bypass it. The field-policy response exposes only allowed types, effective sizes and opaque revision, without storage/scan internals or additional owner IDs.

At upload, combine the immutable issued limits with the latest medical section: use allowed-type intersection and the smaller limit for each remaining type. A newer permissive section never raises this request's issued limit. A stricter section or removed type restricts new uploads; no common type rejects the upload. Operator/scanner capacity and malformed current configuration still fail closed. Preserve verified historical clean downloads independently of new-upload policy.

Capture the effective revision before staging and recheck request/current-section revisions under the existing upload lock before persistence/audit. A policy change during transfer rejects acceptance and compensates the staged object through the existing cleanup path. It does not establish a clean scan or release the file. Later multipart sessions will bind this request/field/effective revision, ownership, checksum, byte bounds and expiry; multipart implementation remains separate.

- Add a small medical attachment-policy resolver/snapshot helper, the two-column migration and model immutability checks.
- Extend `StoreReservationMedicalRequest`, `ReservationMedicalRequestService` and its doctor-controller call for optional narrowing and transactional snapshot creation.
- Wire the patient upload request, `ReservationFileService` and medical request resource to the common authorized resolver, without changing booking/payment/report lifecycle or other upload sections.
- Extend minimal audit allowlists for the policy revision; keep the existing request/file history.
- Verify creation/default/narrowing, source-of-authority rejection, snapshot/hash immutability, cross-owner/reservation denial, direct-service enforcement, exact byte boundaries, stricter/looser policy changes, missing/tampered snapshots, transfer-time revision change/cleanup and audit rollback. Use www-data/testing/SQLite `:memory:` with isolated storage and synthetic fixtures only. No real engine or live file acceptance is inferred.

Approval here would cover the exact two-column source migration and bounded PHP/tests, executed against disposable test databases only. It would not authorize a live migration, backfill, reset/reseed, new dependencies, Compose/build, new medical UI composition or live scanning/storage activation. Live activation needs a separately reviewed operator step and verified schema; do not leave current callers silently applying unpersisted field rules.
